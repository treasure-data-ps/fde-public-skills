# Shared: Customer Requirements Doc Pattern

The audience agent's context files are drafted from the data, then confirmed by the customer. This is done via a customer-fillable markdown file written to `agent_outputs/<customer_slug>/<solution_slug>/requirements.md` (see `local_outputs.md`).

## When to use

Setup mode writes the doc after schema exploration; it is read back when the customer returns it.

## Prerequisites

- `agent_outputs/` bootstrapped (see `local_outputs.md` Step 1)
- `project_state.md` already created (see `project_state.md`)

> 🚫 **Do NOT include auto-generation disclaimers in the requirements doc.** No footer text like "Generated by …" or notes about the discovery queries you ran. The doc must read as a clean, customer-ready questionnaire. Discovery details belong in the chat session or `project_state.md`.

## Step 1: Check for an Existing Doc

Ask:
> Do you already have a filled-out requirements doc for this engagement? If yes, give me its file path (or paste its contents).

If `agent_outputs/<customer_slug>/<solution_slug>/requirements.md` already exists, read it and confirm with the user whether it is the filled version. If filled, skip ahead to reading the filled doc (below).

## Step 2: Write the Customer-Fillable Doc

The calling SKILL provides:
- The doc title: `Audience Agent Requirements - <Customer>`
- The body: one section per `business-context.md` heading, each with the question, the drafted answer and `> _Your answer:_`

The body template may be:
- **A blank form** — sections with `> _Your answer:_` placeholders, customer fills from scratch.
- **A pre-filled draft** — sections with `> _Your answer:_` followed by inferences derived from earlier exploration. The audience-agent body is pre-filled from Setup-mode exploration, with each pre-filled answer tagged either `[INFERRED — please confirm]` (we made a confident guess) or `[NEEDS YOUR INPUT]` (we couldn't infer). The customer reviews / edits / extends.

The pre-filled approach is preferred when the calling SKILL has access to schema or other discovery data that makes meaningful first-draft answers possible. Customers respond faster to a draft they can edit than to a blank form they have to author from scratch.

Write it with the Write tool to:

```
agent_outputs/<customer_slug>/<solution_slug>/requirements.md
```

Body templates should typically include:
- A title line and short purpose statement (pre-filled bodies should explicitly say *"Answers below were drafted from <source> — please review, correct, or expand"* so the customer doesn't think they're seeing input from another customer)
- A target return date placeholder
- N solution-specific sections, each with example answers or pre-filled inferences
- A close-out instruction: "When done, save this file and send it back to the person who shared it with you."

## Step 3: Hand Off

1. Tell the user the file path and that it is ready to share with the customer (the file is plain markdown — it can be emailed, attached, or converted to the customer's preferred format; the filled version must be saved back to the same path).
2. Update `project_state.md`: requirements doc status "sent <date>", Next Action "customer review — run Eval Round 1 meanwhile". The agent is usable with the drafted context while the customer reviews.
3. The customer fills out the doc out-of-band — typically days or weeks. Resume, usually in a new session, when the customer returns the doc.

## Reading the Filled Doc

1. Read `project_state.md` first.
2. Read `agent_outputs/<customer_slug>/<solution_slug>/requirements.md` (ask the user to save the customer's returned version there first if they received it elsewhere).
3. Distill each answer into the matching section of the customer's `business-context.md` (terse, imperative; remove markers; customer answers override inferences; drop sections left unanswered).
4. Present a summary of the changes to the user for confirmation, then update `project_state.md`.
