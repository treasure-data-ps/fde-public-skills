# Shared: Customer Requirements Doc Pattern

Every solution needs customer requirements before the workflow can be configured for production. They are gathered with a customer-fillable markdown file written to `agent_outputs/<customer_slug>/<solution_slug>/requirements.md` (see `local_outputs.md`).

## When to use

Phase 2 — after data exploration (Phase 1), before the minimal workflow push (Phase 3). The filled doc is read back in Phase 4.

## How to ask questions

> **Always use the `AskUserQuestion` tool when gathering requirements from the user — never present questions as a plain text list.** This applies to every solution that uses this pattern.
>
> - Each call renders questions as interactive selectors the user can click.
> - Group up to 4 questions per `AskUserQuestion` call (tool limit). Split across multiple calls if needed.
> - For each question, provide 2–4 pre-populated answer options. Mark the recommended default with `(Recommended)`.
> - The tool always includes an implicit "Other" option so the user can type a custom answer if none of the options fit.
> - Solution-specific `requirements_doc.md` files may add further grouping guidance; follow them if present, otherwise batch logically.

## Prerequisites

- `agent_outputs/` bootstrapped (see `local_outputs.md` Step 1)
- `project_state.md` already created (see `project_state.md`)

> 🚫 **Do NOT include auto-generation disclaimers in the requirements doc.** No footer text like "Generated by …" or notes about the discovery queries you ran. The doc must read as a clean, customer-ready questionnaire. Discovery details belong in the chat session or `project_state.md`.

## Step 1: Check for an Existing Doc

Ask:
> Do you already have a filled-out requirements doc for this engagement? If yes, give me its file path (or paste its contents).

If `agent_outputs/<customer_slug>/<solution_slug>/requirements.md` already exists, read it and confirm with the user whether it is the filled version. If filled, skip ahead to Phase 4.

## Step 2: Write the Customer-Fillable Doc

The calling SKILL provides:
- The doc title (e.g. `<Solution Name> Requirements - <Customer>`)
- The body template — see the solution's `references/requirements_doc.md`

Write it with the Write tool to:

```
agent_outputs/<customer_slug>/<solution_slug>/requirements.md
```

The body should be phrased for the customer to fill in directly — use `> _Your answer:_` placeholders under each question. Pre-fill answers you already inferred in Phase 1 and mark them `[INFERRED — please confirm]`; mark open questions `[NEEDS YOUR INPUT]`.

Body templates should typically include:
- A title line and short purpose statement
- A target return date placeholder
- N solution-specific sections, each with example answers
- A close-out instruction: "When done, save this file and send it back to the person who shared it with you."

## Step 3: Hand Off

1. Tell the user the file path and that it is ready to share with the customer (the file is plain markdown — it can be emailed, attached, or converted to the customer's preferred format; the filled version must be saved back to the same path).
2. Update `project_state.md`: requirements doc status "sent <date>", Next Action "wait for customer answers, then Phase 3 minimal push" (or as the calling SKILL specifies).
3. Continue to Phase 3 (minimal push with safe defaults) unless the calling SKILL says to wait. Phase 4 resumes — often in a new session — once the customer returns the doc.

## Reading the Filled Doc (Phase 4 entry)

1. Read `project_state.md` first.
2. Read `agent_outputs/<customer_slug>/<solution_slug>/requirements.md` (ask the user to save the customer's returned version there first if they received it elsewhere).
3. Map customer answers to workflow parameters per the calling SKILL's section-to-parameter mapping.
4. Present a summary of the planned changes to the user for confirmation before editing the workflow copy.
